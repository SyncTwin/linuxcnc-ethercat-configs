# Кастомная кинематика для LinuxCNC на примере трипода 3-PRS

Штатных кинематик у LinuxCNC десятки, но рано или поздно попадается механизм,
которого среди них нет. У нас это наклонная голова на трёх стойках (3-PRS):
жёсткая платформа на трёх линейных штангах, координаты Z-A-B. Пришлось писать
свой модуль - `ptripodkins.comp` в этой папке. Заодно это готовый разбор того,
как вообще пишется кинематика для LinuxCNC: файл маленький, математика видна
целиком.

## Статус - честно

Модуль собирается, грузится, машина с ним запускается [проверено]. Inverse -
закрытая форма, forward - метод Ньютона, round-trip сходится. На ФИЗИЧЕСКОМ
триподе не откатан - железного трипода у нас нет [не проверяли]. Если соберётесь
подавать питание на реальные приводы: сначала знаки и пределы на холостом ходу,
сверка forward-inverse, лимиты хода штанг.

## Как устроен kins-модуль

Файл `.comp` - это формат halcompile: шапка-описание, разделитель `;;`, дальше
обычный C. Устанавливается одной командой:

```
halcompile --install ptripodkins.comp
```

Нужны заголовки LinuxCNC (`linuxcnc-dev` - там `kinematics.h` и `rtapi_math.h`).
После установки модуль лежит рядом со штатными, и `[KINS]KINEMATICS = ptripodkins`
в ini его находит.

Обязательных функций три:

- `kinematicsInverse(pos, joint, ...)` - из позы платформы посчитать длины штанг.
  Для параллельной кинематики это простая сторона: повернуть точки крепления,
  взять три расстояния. Закрытая форма, считается всегда.
- `kinematicsForward(joint, pos, ...)` - из длин штанг восстановить позу. Вот
  это сторона сложная: аналитического решения нет, работает итерация Ньютона по
  невязкам квадратов длин. Якобиан - численный, система 3×3 решается Крамером.
- `kinematicsType()` - у нас `KINEMATICS_BOTH`: обе стороны есть, LinuxCNC может
  и вести по мировым координатам, и показывать позу по суставам.

Геометрия (радиусы базы и платформы) запечена константами `#define RB / RP` в
начале файла. Поменять - отредактировать и переустановить `.comp`. Для
компонента, который крутится в realtime-потоке, константы времени компиляции -
осознанный выбор: никакого парсинга конфигурации в RT-контексте.

## Грабля, которая стоит дороже всей математики: [TRAJ] HOME

Ньютон в forward стартует с прошлой позы (`Seed from last pose` в коде). А откуда
берётся САМАЯ ПЕРВАЯ поза при старте машины? Из строки `HOME` секции `[TRAJ]`
в ini.

Если её нет, первой итерации не от чего оттолкнуться: forward не сходится,
LinuxCNC печатает ошибку кинематики, а DRO показывает nan. Выглядит это как
«кинематика написана неправильно», и искать ошибку идёшь в математику - которая
в порядке. Мы на это попались [проверено на запусках]; штатный genhexkins ведёт
себя так же, у него сид тоже берётся из `[TRAJ] HOME`.

```
[TRAJ]
COORDINATES = Z A B
HOME = 0 0 350
```

Число в HOME должно быть достижимой позой около реальной домашней - Ньютону нужна
не точность, а окрестность, из которой он сойдётся.

Нюанс напоследок: не у всех кинематик это поле - сид. У последовательных
(genserkins) и у дельты оно играет роль справочной домашней позы, а LinuxCNC 2.9
читает из него только первые три координаты. Одно имя поля - два разных смысла,
в документации об этом ничего.
