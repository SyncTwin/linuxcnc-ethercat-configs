# LinuxCNC в виртуалке: как выделять ядра, чтобы 1 кГц держался

У нас LinuxCNC работает не на голом железе, а в VM на промышленном боксе
(KVM/libvirt, сетевая карта проброшена под EtherCAT). Это удобно - стенд
разворачивается и сносится скриптом, - но realtime в гостевой системе сам собой
не получается. Ниже вся цепочка, как она настроена у нас, с числами до и после.

Число «до», чтобы был понятен масштаб проблемы: гость без изоляции ядер даёт
cyclictest max около 565 мкс [замерено]. С таким разбросом rtapi_app чистый
1 кГц не держит, приводы по DC из OP вылетают.

## Уровень 1: хост - изолированный пул ядер

В GRUB хоста выводим из планировщика все ядра, кроме служебных:

```
isolcpus=<пул> nohz_full=<пул> rcu_nocbs=<пул>
```

Из этого пула нарезаются VM. Проверить, что изоляция применилась после ребута:

```
cat /sys/devices/system/cpu/isolated
```

## Уровень 2: VM получает ЦЕЛЫЕ физические ядра

Правило, на котором всё держится: одной VM отдаются оба HT-потока физического
ядра, никогда - половинки разных ядер. Гипертред-сосед, доставшийся чужой VM,
превращается в источник непредсказуемых задержек, который не виден ни в одном
логе. Какие потоки сидят на одном физическом ядре, видно в
`/sys/devices/system/cpu/cpuN/topology/thread_siblings_list`.

Наш канонический размер - 2 физических ядра (4 vCPU) на стенд:

```
virsh vcpupin <vm> 0 <ht0-ядра-A>
virsh vcpupin <vm> 1 <ht1-ядра-A>
virsh vcpupin <vm> 2 <ht0-ядра-B>
virsh vcpupin <vm> 3 <ht1-ядра-B>
virsh emulatorpin <vm> <неизолированные-ядра>
```

`emulatorpin` - обязательная строка, о которой забывают: служебные потоки qemu
(диск, сеть, VNC) не должны красть время у RT-ядер. Им место на неизолированных
ядрах хоста.

## Уровень 3: изоляция ВНУТРИ гостя

Самая неочевидная часть. Изолировать ядра на хосте недостаточно: гостевое ядро
Linux о договорённостях хоста ничего не знает и планирует свои процессы на все
vCPU подряд - включая тот, где крутится servo-thread. Наши 565 мкс были замерены
именно так: хост изолирован, гость - нет.

Поэтому в госте своя строка GRUB, зеркальная хостовой:

```
isolcpus=<все-vCPU-кроме-0> nohz_full=<те-же> rcu_nocbs=<те-же> irqaffinity=0
```

vCPU 0 остаётся хозяйством (ОС, агент, ssh), последнее физическое ядро - оба его
потока - целиком под RT-поток LinuxCNC, чтобы и внутри гостя у servo-thread не
было гипертред-соседа с посторонней работой.

## Уровень 4: запретить глубокие C-states

Ядро, спящее в C6, просыпается сотни микросекунд - и даёт ровно те редкие
«Unexpected realtime delay», которые невозможно поймать, потому что они приходят
раз в несколько минут на тихой машине. Изоляция от этого не спасает: изолированное
ядро как раз чаще всех спит.

Лечится удержанием `/dev/cpu_dma_latency` в нуле. Пока файловый дескриптор
открыт, PM QoS запрещает глубокий сон всем ядрам. systemd-юнит целиком:

```ini
[Unit]
Description=RT: forbid deep C-states via cpu_dma_latency hold
After=multi-user.target

[Service]
Type=simple
ExecStart=/bin/bash -c 'exec 3<> /dev/cpu_dma_latency && printf "\x00\x00\x00\x00" >&3 && exec sleep infinity'
Restart=always

[Install]
WantedBy=multi-user.target
```

Профиль `realtime` у tuned делает то же самое - если tuned уже стоит, юнит не
нужен. Решение обратимое: остановили юнит - ядра снова могут спать глубоко.

## Проверка

```
cyclictest -m -p 80 -i 1000 -h 400   # headless; latency-test с GUI конфликтует
                                     # с работающим LinuxCNC
```

Гнать минуты, смотреть max, не avg: серво-поток убивает редкий выброс, а не
средняя. После всей цепочки шина у нас держит OP устойчиво, servo-период 1 мс
без «Unexpected realtime delay» [замерено]; на хосте вне VM разгруженная машина
даёт max 15 мкс [замерено].

И симметричное предупреждение из нашего опыта: если приводы не держат OP,
сначала cyclictest, потом всё остальное. Мы дважды копали настройку EtherCAT
там, где был перегружен процессор.
