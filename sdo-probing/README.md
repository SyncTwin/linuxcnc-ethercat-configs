# Проверить привод одними SDO, без LinuxCNC

Четыре скрипта, которым не нужен ни реальный мастер с циклическим обменом, ни
вендорный софт, ни наш. Только утилита `ethercat` из IgH-мастера и python3.
Привод при этом может стоять в PREOP — мейлбокс работает и там.

Зачем это нужно: когда привод приехал, а стенда ещё нет, хочется ответить на
простые вопросы. Живой ли он, крутится ли, какая у него шкала, за какое время
он отвечает. Ниже — как мы это делаем и на что напоролись.

Всё проверено на **Wecon VD3E** (23-битный абсолютный энкодер) и частично на
**Inovance IS620N**. Позиция слейва в примерах — `-p3`, подставьте свою.

## Осторожно

`scale_check.py` и `ladder_timing.py` **крутят мотор**. Вал должен быть свободен:
без нагрузки, без механики, ничего не намотано. Оба скрипта снимают момент по
завершении и в блоке `finally`, и проверяют это чтением statusword — но
единственная настоящая защита это свободный вал.

## Что тут есть

### `read_scaling.sh` — что привод рассказывает о своих масштабах

```bash
bash read_scaling.sh 3
```

Читает объекты масштабирования: `0x608F` (разрешение энкодера), `0x6092` (feed
constant), `0x6091` (электронный редуктор), текущую позицию и режим.

Грабля: у VD3E объектов `0x608F` и `0x6092` **нет вовсе** — «object does not
exist». Разрешение энкодера по шине узнать нельзя, только из ESI или паспорта.

### `scale_check.py` — сколько counts приходится на оборот

```bash
python3 scale_check.py -p 3 --rps 0.5 --seconds 4 --csv run.csv
```

Проходит лесенку CiA 402, включает Profile Velocity (`0x6060` = 3), задаёт
скорость и считает фактическую по приросту `0x6064` относительно часов.

Почему не по `0x606C` (actual velocity): она пересчитывается через ту самую
шкалу, которую мы проверяем, и подтвердит любую ошибку.

Две грабли, на которые мы наступили:

1. **Разгон внутри окна усреднения.** Первый прогон на 0.01 об/с дал расхождение
   6% и почти породил вывод «шкала плывёт». Мотор просто разгонялся первые
   полсекунды, и разгон попал в среднее. Считайте, отбросив начало.
2. **Замер через собственную шкалу ничего не доказывает.** Уставка задаётся как
   `об/с × cpr`, замер делится на тот же `cpr` — множитель сокращается. Такой
   тест подтверждает линейность привода, но не абсолютное число counts на оборот.
   Для абсолютной проверки нужен эталон снаружи цепочки, см. следующий скрипт.

### `gear_probe.py` — эталон, который нельзя обмануть

```bash
python3 gear_probe.py -p 3 --seconds 85 --turns 5
```

Момент снят, вал свободен, скрипт только смотрит счётчик. Вы ставите метку на
валу и проворачиваете его рукой на заданное число оборотов. Скрипт отказывается
работать, если привод под моментом.

Так мы подтвердили, что 23-битный энкодер VD3E действительно даёт 8 388 608
counts на оборот: пять оборотов рукой дали 42 203 264 counts, это +0.6% —
приличная точность для метки и руки.

Этим же способом проверяется электронный редуктор `0x6091`. При 2:1 те же пять
оборотов дали 20 787 053 counts, отношение 2.03. То есть объект работает ровно
по стандарту — хотя замер скоростью этого не показывал, потому что там
коэффициент сокращался.

Совет: одного оборота мало. Наш первый прогон «на оборот» дал 1/6 от ожидаемого
— рука провернула вал градусов на шестьдесят. Пять оборотов и метка снимают
вопрос.

### `ladder_timing.py` — сколько стоит спросить привод

```bash
python3 ladder_timing.py -p 3 --runs 20 --csv ladder.csv
```

Двадцать раз проходит лесенку CiA 402 и засекает время каждой ступени: от записи
controlword до появления нужных битов в statusword. Перед этим меряет базовую
линию — стоимость одного пустого SDO-чтения.

Результат на нашем стенде оказался поучительным: все ступени дали ровно 64 мс,
что равно двум SDO-транзакциям по 32 мс. То есть переходы происходят быстрее,
чем этот метод способен различить, и мы померили собственный прибор. Базовую
линию скрипт печатает именно поэтому — чтобы такой результат было видно сразу.

Разложение по времени (медианы, наш стенд):

| Операция | Время |
|---|---|
| запуск процесса (`/bin/true`) | 0.57 мс |
| `ethercat version` | 1.5 мс |
| `ethercat master` (не трогает шину) | 1.4 мс |
| `ethercat sdos` — перечислить словарь | 5 мс |
| `ethercat upload` — прочитать один параметр | 32 мс |

Спросить структуру дёшево: словарь мастер отдаёт из кеша, собранного при
сканировании. Спросить значение дорого: это реальный обмен через мейлбокс, а у
мастера в фазе Idle он неспешный.

Практическое следствие: чтение полного паспорта привода в 300 параметров занимает
около десяти секунд (60 параметров у нас заняли 1.97 с). Для разового
автодискавери нормально, для периодического опроса на живой шине — нет.

Сколько это будет при поднятом циклическом обмене, мы не мерили.

## Общее правило, ради которого всё затевалось

Подтверждение записи говорит только о том, что сообщение доставлено. Применилось
ли значение, проверяется другим объектом: написали в `0x6060` — читайте `0x6061`,
послали controlword — ждите биты statusword. А абсолютные величины проверяются
эталоном снаружи измеряемой цепочки, иначе замер подтвердит сам себя.
